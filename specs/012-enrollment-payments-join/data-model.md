# Data Model: Enrollment Payments Join

## Payment (`src/collections/Payments/index.ts`) — changed field

| Field          | Before                             | After                                                                 |
| -------------- | ---------------------------------- | --------------------------------------------------------------------- |
| `enrollmentId` | `type: 'number'`, `required: true` | `type: 'relationship'`, `relationTo: 'enrollments'`, `required: true` |

No other `Payments` field changes. `setPaymentDate`, `setRecordedByUser`, `validatePaymentAmount`,
`AmountField`, `StudentCell`, `RecorderCell` are untouched.

`populatePaymentRelations` (afterRead hook) gains a third resolved field, alongside the existing
`studentId`/`userId` blocks:

```
if (doc?.enrollmentId && typeof doc.enrollmentId !== 'object') {
  doc.enrollmentId = await payload.findByID({ collection: 'enrollments', id: doc.enrollmentId, depth: 0 })
}
```

(same try/catch-and-leave-raw-id-on-failure shape as the existing two blocks)

## Enrollment (`src/collections/Enrollments/index.ts`) — new field

New `join` field, added to the `fields` array (no admin.defaultColumns change, matching
`Courses.objectives`/`Courses.phases` precedent):

```
{
  name: 'payments',
  type: 'join',
  collection: 'payments',
  on: 'enrollmentId',
  label: { vi: 'Thanh toán', en: 'Payments' },
}
```

This is a virtual/computed field — Payload resolves it at query time via the `payments.enrollment_id_id`
foreign key. It adds no column to `enrollments` and requires no migration on the `enrollments`
table itself. `src/payload-types.ts`'s `collectionsJoins.enrollments` gains `{ payments: 'payments' }`,
generated by `pnpm generate:types` — never hand-edited.

## Database migration: `payments.enrollment_id` → `payments.enrollment_id_id`

New migration file (after `20260915_220048_add_payments_collection`), registered in
`src/migrations/index.ts`:

- `ALTER TABLE payments ADD COLUMN enrollment_id_id integer;`
- `UPDATE payments SET enrollment_id_id = enrollment_id::integer;`
- `ALTER TABLE payments ALTER COLUMN enrollment_id_id SET NOT NULL;`
- `ALTER TABLE payments ADD CONSTRAINT payments_enrollment_id_id_enrollments_id_fk FOREIGN KEY (enrollment_id_id) REFERENCES enrollments(id) ON DELETE set null;` — matches the `ON DELETE set null` pattern already used for `student_id_id`/`user_id_id` in this table (Edge Case: deleting an enrollment is explicitly out of scope for new cascade behavior — falling back to Payload's existing default for this table is the "no new behavior" choice, not a decision this feature makes).

  **Constraint gap to flag**: `ON DELETE set null` conflicts with `enrollment_id_id`'s own
  `NOT NULL` — the same conflict does not exist for `student_id_id`/`user_id_id` today because
  neither of those was declared `required: true` at the Payload field level the way `enrollmentId`
  is. This must be resolved during `/speckit-tasks`/implementation (either drop `NOT NULL`'s DB
  enforcement to match how Payload's own `required: true` is enforced at the application layer
  only, or use `ON DELETE restrict`/no action) — noted here rather than silently picked, per
  Principle I.

- `CREATE INDEX payments_enrollment_id_idx ON payments USING btree (enrollment_id_id);`
- `ALTER TABLE payments DROP COLUMN enrollment_id;`
- `DROP TYPE` — not applicable (the old column was plain `numeric`, not an enum).

`down()` reverses: re-add `enrollment_id numeric NOT NULL`, backfill from `enrollment_id_id`, drop
the FK/index/column.

## No changes

- `Enrollments.access`, `Payments.access` — unchanged (see research.md).
- `Payments.admin.defaultColumns` — unchanged; `enrollmentId` already listed there today and
  continues to display (now via `populatePaymentRelations`, same as `studentId`/`userId`).
- Seed data (`src/seed/`) — out of scope unless a seed script currently writes `payments` with a
  raw-number `enrollmentId`; verify during implementation and update the call site's value shape
  only (still passing an enrollment id — Payload accepts a bare id for a `relationship` field on
  write, so no seed script content change is expected).
